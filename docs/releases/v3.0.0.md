# v3.0.0 — A smaller installer, with a one-time import from v2

## Highlights

- **New installer engine.** The Go installer is now a set of packages with
  checked boundaries (`featuremap.json`). Each tool has one folder,
  `installer/tools/<name>/`, with its catalog entries, its pins and its shell
  fragments. The menu, the categories, the review screen and the progress
  display are the same as in v2.
- **No Resume and no Abandon.** After an interruption, run setup again. Setup
  inspects the system and continues. When a native command did not report its
  end, setup names the step and asks you to confirm that the command exited.
- **Copy-ready command blocks.** The review shows each system package command
  in one block that you can copy.
- **Applications from Homebrew casks on macOS.** VS Code, Ghostty and
  OpenWhispr now come from the casks `visual-studio-code`, `ghostty` and
  `openwhispr`, as Zen and T3 Code did before. The apps go to `/Applications`
  and update themselves.
- **One CI workflow.** `ci.yml` has the `lint`, `e2e`, `clean` and `migrate`
  jobs. Each `e2e` job installs each tool of its system, runs it, updates it
  and removes it, then compares the home folder with its baseline.

## Breaking changes

- **State schema 2.** The state file has a new format: one record for each
  managed target, the names of the system packages that setup installed, and
  pending marks. Receipts, journals, transactions and saved plans are gone.
  The v2.3.0 setup refuses a schema-2 state. Release v3.0.0 reads a v2 state
  only to import it.
- **Command surface.** `machine` and its JSON protocol are gone. Setup with no
  argument opens the menu. Automation uses these commands:

  | Command | Result |
  |---|---|
  | `plan [--select=<ids>] [--remove-shared=<ids>] [--replace=<ids>]` | Prints the plan and changes nothing. |
  | `apply --yes [--select=<ids>] [--remove-shared=<ids>] [--replace=<ids>]` | Applies the selection. |
  | `update --yes [--replace=<ids>]` | Applies the reviewed versions of the checkout. |
  | `check` | Inspects the installation and changes nothing. |
  | `restore-v2 --yes` | Gives release v2 back after an import. |

  Without `--yes`, `apply`, `update` and `restore-v2` print the preview. Exit
  code 0 is done. Exit code 1 is a failure, or a difference that `check`
  found. Exit code 3 tells you to run the same command again.
- **Setup never removes a system package.** This applies to APT packages,
  Homebrew formulae and casks, and applications from Windows vendor
  installers. When nothing needs a recorded package, the review shows its
  removal command, and you run it. Until then the package stays as a retained
  resource, with its requirements and its configuration.
- **Pinned system routes refuse a downgrade.** Update reports the installed
  and the pinned version of the Linux Code and Tailscale DEBs and of the
  Windows runtimes.
- **One test variable.** `DOTFILES_TEST_NATIVE=1` replaces each earlier
  `DOTFILES_TEST_*` variable for native tests.

## macOS cask moves

| Application | v2 | v3.0.0 |
|---|---|---|
| VS Code | pinned archive, `update.mode: none` | cask `visual-studio-code`, updates itself |
| Ghostty | pinned DMG | cask `ghostty`, updates itself |
| OpenWhispr | pinned archive | cask `openwhispr`, updates itself |

Setup accepts only the `homebrew/cask` tap, installs with `--require-sha` and
`--no-binaries`, and checks the reviewed developer signature. It links the
`code` and `ghostty` commands to the new apps. On macOS, setup no longer
manages the VS Code `update.mode` field. Linux and Windows keep their pinned
routes. Read [application casks on macOS](../security/supply-chain.md#application-casks-on-macos).

## Removed release machinery

The release manifest, `release/`, `release.yml`, the release script, the
safeguard scripts, the checked-in rulesets, `.github/check-identities.json`
and `make release-check` are gone. The owner now makes the immutable tag and
publishes the notes in one GitHub release action. Read
[RELEASING.md](../RELEASING.md). The required checks changed to the jobs of
`ci.yml`. Read [branch protection](../security/branch-protection.md).

## Compatibility and upgrade

The supported platforms do not change: Apple Silicon macOS, Ubuntu and Debian
on amd64 or arm64, and native Windows amd64. WSL uses the Ubuntu and Debian
items. Use `setup.sh` on macOS and Linux, and `setup.ps1` on Windows.

This release imports only the state of v2.3.0 (commit `fb15ce5`). To move
from v2:

1. With the `v2.3.0` checkout, choose **Update tools**, finish or abandon each
   interrupted operation, and run **Check**.
2. Update the checkout to `v3.0.0` and open setup. Setup shows the import for
   review and changes nothing before you approve.
3. Approve the import. Setup builds the private tools again, verifies them and
   then switches. Release v2 stays active when a build fails.
4. Run **Check**.

The import keeps your selection, your changed content, the system packages
and the Sentinel files. It never deletes the v2 folders in the state folder:
delete them yourself after the fallback closes. On the Mac, the three
applications above keep their v2 payloads in the import run. A later **Update
tools** run offers each cask install. **Choose tools** keeps the v2 payload.

`restore-v2 --yes` and then `git checkout v2.3.0` give release v2 back. The
first confirmed **Choose tools** or **Update tools** run that changes
something closes this fallback. Migrate Ubuntu and WSL first, then the Mac, then
Windows. Follow [From v2 to v3.0.0](../UPGRADING.md#from-v2-to-v300) for each
step.

To move from a release before v2.3.0, update to `v2.3.0` first.

Release v3.1.0 will delete the import and `restore-v2`. Import each machine
and close each fallback before you update to v3.1.0.

## Not verified natively

These notes do not claim a native result. When they were written, these items
had no native proof:

- The `e2e`, `clean` and `migrate` jobs of `ci.yml` on GitHub runners. The Go
  tests of the packages use fakes and temporary folders.
- The import of a real v2 installation on the Ubuntu, WSL, Mac and Windows
  machines of the owner. The `migrate` jobs use a small selection.
- The three cask installs beside the v2 application links on a real Mac, and
  the three signing requirements against the vendor-signed bundles.
- The match of the Sentinel checkout record on macOS and Windows. It ran only
  on Linux.
- Build Tools elevation on a managed Windows laptop. If elevation fails, the
  tools that need the compiler stop.
- The live GitHub branch protection after the change of the required checks.
- Reboots, first-time permission grants and visual checks.
